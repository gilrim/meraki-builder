# meraki-builder

Buildroot board support, utilities, and image-generation tooling for selected Cisco Meraki switches and routers.

This fork adds a self-contained MS42P development workflow on the `ms42p-dev` branch. The repository is now the authoritative source for its Buildroot board files and custom packages. A complete MS42P image can be produced with one interactive command:

```bash
make all
```

The build can also be run non-interactively or one stage at a time.

## Supported hardware represented in this repository

The shared `buildroot/board/meraki/ms220` integration contains runtime handling for several related VCore-III/Vitesse switch families, including:

- MS220-8 and MS220-8P
- MS220-24, MS220-24P, MS220-48LP, and MS220-48FP
- MS22 and MS22P
- MS42 and MS42P
- MS320-24, MS320-24P, MS320-48LP, and MS320-48FP

The automated workflow documented below is currently focused on the **MS42P** and its known-good RedBoot/NOR layout. Do not assume that the generated 16 MiB image is suitable for every model listed above.

Buildroot board support also remains present for MX80 and MX84 systems, but those targets are outside the automated MS42P workflow.

---

# MS42P firmware overview

The resulting firmware consists of four main layers:

1. A 256 KiB RedBoot loader.
2. A Linux 3.18.123 compressed kernel with a 32-byte Meraki `SPIM` header.
3. An 8 MiB read-only SquashFS generated by Buildroot 2023.02.4.
4. A 5 MiB JFFS2 partition used as the writable overlay for `/etc` and `/root`.

At runtime, the management CPU loads donor Meraki/Vitesse kernel modules, mounts the Click filesystem at `/click`, and writes the switch graph from `/etc/switch.template.gz`. The optional web interface adds `configd`, `uhttpd`, and the compiled `postmerkos-ui` frontend.

The switch ASIC dataplane is configured through Click handlers such as:

```text
/click/switch_port_table/dump_pports
/click/switch_port_table/set_port_phy_cfgs
/click/switch_port_table/set_vlan_allports_conf
```

The Linux userspace acts primarily as the management and control plane. Packet forwarding is handled by the Vitesse/Jaguar switching hardware.

# What changed in the `ms42p-dev` build workflow

The older process relied on a separate script bundle that cloned multiple versions of `meraki-builder`, overlaid one repository over another, and applied compatibility edits while the build was running.

This fork instead follows these rules:

- The checked-out `Gadorach/meraki-builder` tree is authoritative.
- The build no longer clones Hall's or Hal Martin's `meraki-builder` repository.
- Custom Buildroot packages are synchronized directly from `buildroot/packages/`.
- Required package `Config.in` entries are registered automatically and idempotently.
- The `clickswstatus` and `find_hdr` package layouts are normalized in the repository rather than renamed during every build.
- The released PostmerkOS Click compatibility adjustment is maintained directly in `configd`.
- `S15configd` and `S16uhttpd` are maintained as an optional web feature overlay.
- The Buildroot post-image script assembles and validates the complete 16 MiB NOR image.
- Donor files are treated as binary inputs. By default, only `/lib/modules` and the RedBoot loader are imported.
- The optional web UI is pulled from `Gadorach/postmerkos-ui`, branch `ms42p-dev`.
- Build outputs, downloaded archives, extracted donor files, and source checkouts remain outside the Git-tracked source tree.

# Prerequisites

The workflow is designed around Bash scripts. It works even when the interactive shell is Fish because Make invokes the scripts with Bash-compatible shebangs.

## CachyOS or Arch Linux

Install orchestration tools with:

```bash
make deps
```

The old OpenWrt toolchain, Linux 3.18 build, and Buildroot 2023.02.4 host tools are most reliable inside an Ubuntu 22.04 distrobox. The complete build detects Arch/CachyOS and offers to create and use:

```text
name:  meraki-build
image: ubuntu:22.04
```

The complete build can also be run inside that environment explicitly:

```bash
make distrobox
```

## Debian or Ubuntu

Install required packages with:

```bash
make deps
```

A direct native build is normally appropriate on Ubuntu 22.04.

## Host tools

Use the diagnostic target to check the current environment:

```bash
make doctor
```

Important tools include:

- Git
- GNU Make and a C/C++ build toolchain
- Python 3
- tar, xz, bzip2, and cpio
- rsync
- binutils/readelf
- squashfs-tools
- mtd-utils, including `mkfs.jffs2`
- curl or wget
- Node.js 20 or newer when building the optional UI

When a sufficiently new Node.js installation is unavailable, the UI stage downloads a project-local Node.js 22 archive under `.work/build/tools/`.

# Quick start

Clone the fork and select the development branch:

```bash
git clone https://github.com/Gadorach/meraki-builder.git
cd meraki-builder
git checkout ms42p-dev
```

Run the complete interactive build:

```bash
make all
```

The build asks whether to include the web interface. It also offers to:

- install missing dependencies;
- clone the pinned kernel/OpenWrt source;
- run the complete kernel and Buildroot workflow in Ubuntu 22.04 distrobox on CachyOS/Arch;
- build missing kernel artifacts;
- download the known donor firmware when no local donor is present;
- download Buildroot 2023.02.4 when it is not already cached.

The final image is written under `artifacts/`, and its path is recorded in:

```text
artifacts/latest-image.txt
```

## Explicit base image

```bash
make base
```

This builds without `configd`, `uhttpd`, the UI assets, or the web service init scripts. `pd690xx` remains enabled because it is also required by the normal PoE startup and status scripts.

## Explicit web image

```bash
make web
```

This clones or updates:

```text
https://github.com/Gadorach/postmerkos-ui.git
branch: ms42p-dev
```

It runs `npm ci` and `npm run build`, then installs the compiled output at `/www` in the generated root filesystem.

# Build stages

Every major stage can be invoked independently.

## 1. Check the environment

```bash
make doctor
```

## 2. Install dependencies

```bash
make deps
```

## 3. Prepare the pinned kernel/OpenWrt source

```bash
make sources
```

Default source and revision:

```text
https://github.com/halmartin/switch-11-22-ms220.git
d167da8b01e46e29bf3347b8952ce9063ba75d29
```

The checkout is stored in:

```text
.work/sources/switch-11-22-ms220/
```

## 4. Build the OpenWrt toolchain and compressed kernel

```bash
make kernel
```

This stage:

1. Loads `config-elemental-3.18` into the old OpenWrt tree.
2. Builds the MIPS little-endian cross-toolchain.
3. Configures Linux with `msxx_defconfig`.
4. Builds `vmlinuz`.
5. converts it to `vmlinuz.bin`;
6. verifies the compressed-kernel entry point is `0x81000000`;
7. creates the local `linux-3.18.123.tar.bz2` input used by Buildroot for kernel headers.

Kernel artifacts are written to:

```text
artifacts/kernel/
```

## 5. Prepare the donor binary inputs

```bash
make donor
```

Accepted local inputs include:

```text
inputs/postmerkOS-20240818.bin
inputs/donor-firmware.bin
inputs/good-rootfs.squashfs
```

A full firmware donor must be exactly 16 MiB. The script extracts:

- the 8 MiB SquashFS region at offset `0x300000`;
- the 256 KiB RedBoot region at offset `0x000000`;
- the donor `/lib/modules` tree.

The following modules are required:

```text
elts_meraki.ko
merakiclick.ko
proclikefs.ko
jaguar_dual/vc_click.ko
jaguar_dual/vtss_core.ko
```

When only a standalone SquashFS is provided, the script accepts `inputs/loader1.bin` or offers to download the known RedBoot loader.

The donor firmware is not committed or redistributed by this repository.

## 6. Build the optional UI

```bash
make ui
```

This stage selects `Gadorach/postmerkos-ui:ms42p-dev`, builds it, and places the generated files in:

```text
.work/build/postmerkos-ui/
```

The UI is not copied into the source-controlled board overlay. It is added to the generated overlay only when `INCLUDE_UI=1`.

## 7. Verify and record local build inputs

```bash
make verify-inputs
```

This validates the local kernel, kernel-header archive, 256 KiB loader, required donor modules, and optional compiled UI. It writes a SHA-256 manifest to:

```text
artifacts/build-inputs.sha256
```

The preparation stage runs this check automatically. No second `meraki-builder` checkout is used as a comparison source.

## 8. Prepare Buildroot

Base build:

```bash
INCLUDE_UI=0 make prepare
```

Web build:

```bash
INCLUDE_UI=1 make prepare
```

This stage:

1. downloads and extracts Buildroot 2023.02.4 if needed;
2. synchronizes `buildroot/board/meraki` from this repository;
3. synchronizes all custom packages from `buildroot/packages`;
4. registers `package/Config.in.ms42p` in upstream Buildroot;
5. applies maintained Buildroot patches idempotently;
6. creates a generated overlay containing donor modules;
7. optionally adds compiled UI assets and web init scripts;
8. writes an absolute local kernel-header archive path into `.config`;
9. selects the appropriate optional packages;
10. runs `make olddefconfig`.

The prepared Buildroot tree is:

```text
.work/build/buildroot-2023.02.4/
```

## 9. Build the rootfs and complete firmware image

```bash
make rootfs
```

Buildroot generates `rootfs.squashfs`, then invokes:

```text
buildroot/board/meraki/ms220/post-image.sh
```

The post-image script consumes the locally built kernel and loader and creates the complete NOR image. It performs size and entry-point checks before assembly.

## 10. Validate the completed image

```bash
make validate
```

Validation checks include:

- exact 16 MiB image size;
- `SPIM` header at offset `0x40000`;
- load and entry addresses of `0x81000000`;
- embedded kernel length and SHA-256 match;
- SquashFS magic at offset `0x300000`;
- presence of required init scripts, donor modules, and PoE utility;
- presence or absence of the web stack according to `INCLUDE_UI`.

---

# NOR layout

The automated MS42P image uses this layout:

| Start | End | Size | Contents |
|---:|---:|---:|---|
| `0x000000` | `0x03ffff` | 256 KiB | RedBoot loader |
| `0x040000` | `0x2fffff` | 2816 KiB | 32-byte SPIM header and compressed kernel |
| `0x300000` | `0xafffff` | 8 MiB | SquashFS root filesystem |
| `0xb00000` | `0xffffff` | 5 MiB | Empty JFFS2 persistent overlay |

The generated kernel header contains:

```text
magic:        SPIM
load address: 0x81000000
length:       compressed vmlinuz.bin length
entry point:  0x81000000
reserved:     16 zero bytes
```

The post-image script refuses to build when:

- the loader is not exactly 256 KiB;
- the compressed kernel plus header exceeds 2816 KiB;
- the SquashFS exceeds 8 MiB;
- the kernel entry point differs from `0x81000000`;
- the final image differs from 16 MiB.

# Donor overlay policy

The default policy is:

```bash
DONOR_ETC_POLICY=modules
```

Only donor kernel modules are copied into the generated Buildroot overlay. The checked-out repository remains authoritative for `/etc`, startup scripts, the Click template, and other userspace files.

A compatibility fallback is available:

```bash
DONOR_ETC_POLICY=missing make web
```

This copies the donor `/etc` tree into the generated overlay first. The repository's source-controlled board overlay is then applied afterward and overwrites matching files. This can help identify donor-only dependencies without allowing the donor to replace maintained repository files.

The preferred long-term state is `DONOR_ETC_POLICY=modules`.

# Editing the Buildroot configuration

Prepare the tree first, then open menuconfig:

```bash
INCLUDE_UI=1 make prepare
make menuconfig
```

To preserve configuration changes in the repository:

```bash
cp .work/build/buildroot-2023.02.4/.config \
  buildroot/board/meraki/ms220/buildroot-config
```

Before committing, replace machine-specific values such as the absolute kernel-header archive path with a neutral placeholder. `scripts/prepare-buildroot.sh` supplies the correct local path during every build.

# Adding a custom package

Place the package under:

```text
buildroot/packages/<package-name>/
```

Add its Kconfig source line to:

```text
buildroot/packages/Config.in
```

The preparation stage copies each package directory into upstream Buildroot's `package/` tree and registers the shared custom `Config.in` file. Static line-number-based patches to upstream `package/Config.in` are not required.

# Optional web stack

When `INCLUDE_UI=1`, the generated rootfs contains:

```text
/www/index.html
/bin/configd
/usr/bin/uhttpd
/etc/init.d/S15configd
/etc/init.d/S16uhttpd
```

At runtime:

- uhttpd serves the frontend on TCP port 80;
- configd listens for WebSocket clients on TCP port 4001;
- configd logs to `/tmp/configd.log`;
- uhttpd logs to `/tmp/uhttpd.log`;
- persistent switch configuration is stored in `/etc/switch.json` on the JFFS2-backed overlay.

The current web service has no authentication or TLS. Keep it on a trusted management network.

---

# Persistent JFFS2 behavior

The SquashFS is read-only. JFFS2 provides writable upper directories for `/etc` and `/root`.

When testing a newly built SquashFS, remember that an existing file in JFFS2 can override the new file from SquashFS. Unexpected behavior after an update may be caused by stale persistent configuration rather than the newly built image.

A full 16 MiB image produced by this build contains an empty JFFS2 filesystem. Flashing only the loader, kernel, or SquashFS regions can preserve existing JFFS2 content.

# Troubleshooting

## OpenWrt or Buildroot host tools fail on CachyOS

Run the entire workflow in Ubuntu 22.04 Distrobox:

```bash
make clean
INCLUDE_UI=1 make distrobox
```

`make all`, `make base`, and `make web` now offer to enter Distrobox before any build stage on Arch/CachyOS. This is important for Buildroot as well as the legacy kernel: Buildroot 2023.02.4 bundles binutils 2.38, which does not compile cleanly with GCC 16 because `static_assert` is treated as a C keyword.

When changing between host and container builds, the rootfs script records the build environment and automatically cleans incompatible Buildroot output before rebuilding.

## Buildroot reports missing custom Kconfig symbols

Run:

```bash
make prepare
```

The preparation stage must synchronize `buildroot/packages/` and register `package/Config.in.ms42p` before `olddefconfig` or a rootfs build.

## The UI loads but shows no WebSocket connection

Confirm the image was built with `INCLUDE_UI=1`, then check on the switch:

```sh
ps | grep configd
cat /tmp/configd.log
netstat -lnt | grep 4001
```

Also confirm `/etc/init.d/S15configd` exists and that the Click graph was initialized before configd started.

## configd exits while reading storm control

This fork directly includes compatibility for released PostmerkOS Click graphs that provide `set_port_storm_control` but not `dump_port_storm_control`. Confirm the rootfs contains the `configd` built from this branch rather than an older externally patched package.

## A corrected `/etc` file does not appear after flashing

The previous version may still exist in the JFFS2 upper layer. Inspect or erase the persistent overlay before concluding that the SquashFS build is wrong.

## Rootfs exceeds 8 MiB

Remove unnecessary packages or assets. The post-image script intentionally refuses to truncate an oversized SquashFS.

# Safety and recovery

A malformed bootloader, kernel header, partition layout, or root filesystem can make the switch unbootable. Maintain a verified full flash backup and a known-working external SPI programming method before testing new images.

The automated image target does not flash hardware. It only builds and validates a firmware file.

# Other board targets

The historical Docker and board files for MX80, MX84, and other switch experiments remain in the repository. They have not been integrated into the MS42P top-level Makefile and should be treated as separate workflows.

## Integrated firmware updater

The MS42/MS42P firmware updater is a normal, always-enabled Buildroot package.
Its repository source is stored under:

```text
buildroot/packages/fwupdate/
```

`make prepare` copies it into the extracted Buildroot `package/` tree and the
shared custom Kconfig menu registers it automatically. The board configuration
enables both `BR2_PACKAGE_FWUPDATE` and `BR2_PACKAGE_FWUPDATE_CURL`, along with
shared-plus-static C libraries so the RAM-resident `fwflash` helper can be
statically linked. No separate stage-15 integration script is required.

The installed commands are:

```text
fw_update
fw_update_http
fw_update_tftp
fw_update_sftp
fw_update_status
```

Host-side syntax, static-link, checksum-sidecar, and repository-index tests can
be run with:

```bash
make test-fwupdate
```

See [`docs/FIRMWARE-UPDATER.md`](docs/FIRMWARE-UPDATER.md) for operation,
publication, and first-hardware-test procedures. Firmware checksum sidecars are
generated from the artifact directory so they contain only the image basename,
which is required by the updater's strict sidecar parser.
